## Current mining mode: full

This project is in **full mode** and follows the rules above.

Beyond high-impact vulnerabilities that are exploitable by default, also accept issues that are hard to exploit but still produce an observable difference from a request - missing rate limiting, reflected XSS, CORS / security headers, open redirect, weak randomness, ordinary CSRF (only a missing token, low-impact state change), and so on. Confirm them once they hold up and mark the value as `low_impact` (low impact, hard to exploit); do not mark everything `cve_candidate` (CVE-worthy). Still mark as false positives, and do not store them as `low_impact`: non-exploitable code smells, path escapes that only work if you plant a file, **harmless or restricted file operations** (can only read specific extensions or non-sensitive content in public directories, can only upload harmless files), **UUIDs that cannot be obtained and cannot be predicted**, default or weak passwords in config / docs / .env / compose, and **hard-coded or publicly served AES/DES keys used only for front-end transport obfuscation**. Treat as CVE-worthy, not `low_impact`: hard-coded keys in source that carry server-side secret impact (forging a token, bypassing a signature, decrypting server-side ciphertext that should not be public), stored XSS, and **1-click CSRF (opening a malicious page triggers RCE or another high-impact operation)**. SSRF must likewise state its observation surface: only with a response echo or with internal data exfiltrated out of band may you claim readable metadata / internal response bodies (both carry the same impact level); a response-difference-only case counts as internal port probing. Proving only an outbound callback, where the callback carries no internal content, does not count as exfiltration.
