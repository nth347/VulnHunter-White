# Report / Advisory / CVE formats

These formats apply both when submitting a vulnerability and when later rewriting the same document on the vulnerability detail page. Do not paste the three documents into one another.

## Report (report_md / report.md)

- Must be in English, structured to match `templates/vuln-report.en.md`, and must contain at least: `## Summary`, `## Vulnerability description`, `## Impact`, `## Vendor full name`, `## Known affected products and versions`, `## Internet asset proof`, `## Technical details`, `## Same-root-cause affected points`, `## Reproduction proof`, `## Remediation`, `## Notes`.
- **The title must be in English**: the `title` on `SubmitVuln`, the report YAML `title` and the level-one heading `# ...` must all summarize the vulnerability in English (type + location/entry point), for example `Pre-auth SQL injection in XXOA`, `Unauthorized access in UserController`. Product names, class names and CVE ids stay verbatim.
- `## Internet asset proof` reuses the project-wide shared fingerprints in `docs/app-fingerprints.json` directly (the system collects them once after recon: title/app, body features of the default page HTML, static assets, repository favicon, plus the FOFA query used for internet search). Do not re-identify them per finding and do not invent hashes; the query must not contain an OR relation. Both title/app and `body="page feature"` may be used; do not default to stacking title && app && icon_hash into something too narrow.
- "Environment setup" only references `docs/lab.md`; do not restate images, ports, credentials or start commands. When that document does not exist yet, write "the dynamic environment has not been written to disk yet, see `docs/lab.md`".
- Write the vulnerability description in two paragraphs: the first outlines the vendor/organization and the product, the second outlines the cause and the consequence. For SQL injection, state in the impact whether an OS shell can be obtained. For SSRF, state the observation surface in the impact: response echo / internal data exfiltrated out of band / response difference only (internal port probing). A response echo and out-of-band exfiltration carry the same impact level.
- **Indirect consumer** (JDBC connection pools, SQL firewalls, parsing libraries and similar components with no direct HTTP/RPC entry point, where full exploitation depends on an upstream business application passing in attacker input): state explicitly under **`### Trigger conditions`** that the component cannot be reached with a direct request and that an exploitable injection point must be found in the upstream business application. On Confirm the Reviewer sets `exposure_mode=indirect_consumer` and lowers the CVSS / tier per those constraints.
- Only when the mining path is historical-bypass, additionally align with `templates/vuln-report-bypass.md` on top of every section above: under `## Technical details` the **first** subsection is `### Patch bypass analysis` (the original vulnerability and its patch, and why it is bypassed or still unfixed), followed in order by `### Source → Sink`, `### Vulnerable code`, `### Full PoC description`, `### Trigger conditions`. Do not substitute a free-form note for the full report. The second paragraph of a bypass report's description must explain its relationship to the historical vulnerability document.
- **Local verification (harness) confirmation**: `## Technical details` must contain `### Vulnerable code`, giving the **full in-repo relative path** of the vulnerable code and pasting the source verbatim into a fenced code block. `ConfirmVuln(evidence_level=harness)` is rejected when the path or the code block is missing. Static and lab-dynamic confirmations do not require this subsection.
- **Fill in `## Reproduction proof` according to the verification mode**:
  - **Local verification (harness)**: under `### Trigger steps` add `#### Local verification`, paste the key stdout from the harness run (the important lines only), and under `**Why the harness proves the vulnerability exists**` explain how the harness builds its input, which source functions it calls, what dangerous runtime behaviour was observed (exception / changed return value / tampered state / sensitive data leaving the process) and how that behaviour maps onto the root cause in the source. **Do not** describe how to use the PoC or its CLI arguments.
  - **Lab dynamic (dynamic/mcp)**: under `### Trigger steps` add `#### Dynamic verification`, give the key HTTP request (use `TARGET` for `Host`; replace long strings with placeholders) and how to run the PoC (`python poc.py -u <target>`, plus `-c/--cmd` for RCE), and under `**Why the PoC exploits this vulnerability**` analyse which request field is the attacker-controlled input, which path through the source reaches the sink, and how the PoC's actual output maps onto the impact.
  - Fill in whichever of the two applies and delete the part that does not.

## English GitHub Advisory (advisory_md / advisory.md)

- Must be a GitHub Advisory form draft in English, structured to match `templates/vuln-advisory.md`, containing at least: `## Title`, `## Description` (`### Summary` / `### Details` / `### Vulnerable code` / `### PoC` / `### Impact`), `## Affected products`, `## Severity / CWE` (including the **CVSS 3.1** vector string; ConfirmVuln computes the base score and severity label from the vector, so do not fill in a score by hand - leave the vector empty for the Reviewer when unsure).
- `### Vulnerable code` must give the **full in-repo relative path** of the vulnerable code (not just a class or method name) and paste the source verbatim into a fenced code block - the same level of evidence as `### Vulnerable code` in the report, never omitted.
- `### PoC` must contain the full HTTP request in an `http` code block; replace long strings inside the request (roughly 80+ characters) with descriptive placeholders such as `<BASE64_PAYLOAD>`.
- The Advisory is a separate document from `report.md` - do not paste one into the other. Keep the section headings exactly as the template has them.

## CVE JSON (cve.json)

- Align with `templates/cve.json`. Keep the uniform placeholder `VULNHUNTER_PENDING` for unknown fields.
- During agent mining / review rounds, fill fields one at a time with `ReadCveRecord` / `SetCveRecordField`; do not Write the whole `cve.json`.
- For CVSS write only `containers.cna.metrics[0].cvssV3_1.vectorString` (the `CVSS:3.1/...` base vector); `baseScore` / `baseSeverity` are computed by the system per CVSS 3.1, and a hand-filled score or a 3.0/4.0 path is rejected.
- `containers.cna.affected[0]` must satisfy CVE 5.2: **vendor + product**, or **packageName + collectionURL** (such as `https://pypi.python.org`). It may mirror the advisory's `## Affected products`.
- `containers.cna.descriptions[0].value` must be a **detailed English description** a CNA can review - not a one-line summary, and not the report or Advisory markdown headings pasted in. The field holds **at most 4096 characters**; replace long strings (roughly 80+ characters) with placeholders such as `<BASE64_PAYLOAD>` / `<JWT_TOKEN>`, and note that the system truncates over-long text. Write it in this order:
  1. **Product**: vendor/organization, product name, affected versions.
  2. **Root cause**: vulnerability type (CWE), the control that is missing or bypassed, the key file/function.
  3. **Vulnerability chain**: entry point (endpoint / parameter / authentication prerequisite) → intermediate processing → sink; state why it completes under a default deployment.
  4. **Vulnerable code**: full in-repo relative path (such as `src/.../File.ext` or `app/utils/backup.py:42`) plus the corresponding source verbatim; not just a class or method name or a one-line summary.
  5. **PoC**: with an HTTP surface, give the full raw HTTP request (method, path, required headers, body; use `TARGET` for `Host`); replace long strings (roughly 80+ characters) with placeholders such as `<BASE64_PAYLOAD>` / `<JWT_TOKEN>`. With no HTTP surface (component library / public API) give a reproducible API or call chain - do not leave it empty; and do not copy the inline/mock code from `harness.py` into `poc.py`. With neither an HTTP nor an install surface, `poc.py` need not be written to disk.
  6. **Impact**: what the attacker can do after successful exploitation; state the remaining preconditions honestly and do not overstate.
- `supportingMedia[0].value` is the same content as HTML: paragraphs in `<p>`, and **both the vulnerable code and the HTTP/API PoC inside `<pre>`** (one block each, not crammed into a single plain-text paragraph). Do not just copy one line of plain text.
- `problemTypes[0].descriptions[0].description` still holds only the English CWE weakness name, not the whole vulnerability description.
