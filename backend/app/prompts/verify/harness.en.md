## Verification mode for this project: local verification

The project chose **local verification**: no Docker lab is built and no HTTP is sent to a Docker `target_url`. **L1/L2 by default** do not run `poc.py -u` against a lab and do not use the debug MCP. **L3 integration verification** has the system start a loopback service inside the integration sandbox and run `poc.py`; on success `evidence_level=dynamic`. **This overrides the "dynamic verification ladder" above**:

### Verification depth (harness_depth)

| Depth | Applies to | Method | Evidence |
|------|------|------|------|
| **sink** (default) | a single function / string or byte API | RunCode harness: inline or mock | `harness` |
| **module** | the chain crosses several `src/` modules, with no HTTP request-object entry point | import the project modules inside the harness and drive the payload through the real call order | `harness` |
| **integration** | the component can start a CLI/service; the full chain must pass an HTTP management surface; a `poc.py -u` exists | system integration sandbox: temporary dependencies → start a service on `127.0.0.1:$PORT` → run the PoC | **`dynamic`** |

Report structure: `#### Local verification (sink)` or `#### Local verification (module chain)`; after a successful L3 add `#### Dynamic verification (integration)`.

L3 must pass `ConfirmVuln(harness_depth=integration, integration_start=...)`, optionally with `integration_setup` (such as `npm ci`). **Do not** leave a long-running service on the host machine; only fall back to the host when the sandbox is unavailable and `local_service_url` is already written in `env/env.json`.

1. First Read the report, `poc.py` and the source, and confirm `file_path` and the code excerpt really exist. If the file is missing or the code does not match → false positive.
2. Design the verification yourself in the **target language**. By default: extract the suspect function or the smallest compilable excerpt, mock the database / filesystem / framework dependencies, and drive the sink with several payloads. **Only when the component's public entry point itself consumes an HTTP / WebSocket / RPC request object** (such as `ValidateRequest`, middleware, `ServeHTTP`, or a Filter taking `HttpServletRequest`) should you add one **in-process request-level reinforcement** (see the last section); APIs that only consume bytes or strings - YAML, crypto, templating, deserialization - must **not** be wrapped in another layer of HTTP.
3. Execute with `RunCode` in a single-use sandbox (Python / PHP / JS / Ruby / Go / Java / Bash / C). **C uses `language=c` (gcc + glibc, no third-party libraries such as OpenSSL).** **There is no rustc / g++**; `language=rust` / `c++` or probing rustc returns `unsupported_language` - then `ConfirmVuln(evidence_level=static_only)`, do not keep calling RunCode, do not false-positive for this, and do not restate Rust in another language. Do not run the harness in the host Bash/PowerShell. **The stdout/stderr the script itself prints (labels, steps, verdicts) must be bilingual: English by default, with a `--zh` flag to switch to Chinese** (Python `argparse`; other languages scan argv / `process.argv` / `os.Args`). **A JavaScript table must be a `[en, zh]` array, never `(en, zh)`** (the comma operator keeps only the Chinese string, and `msg()` then destructured by character prints single characters). Comments, docstrings and `--help` stay in English; source excerpts, payloads and the target's echoed output are not translated.
4. **The output must come from runtime data**: the evidence that reaches stdout must be the actual value produced after calling the extracted function / sink (return value, queried rows, command echo, rendered HTML, exception text). It is **forbidden** to print only a fixed string (`VULNERABILITY CONFIRMED` / `SUCCESS` / `PASS`); **forbidden** to hard-code a success field (`success = True`, `{"success": true}`, `confirmed: true`); **forbidden** to write the expected echo as a literal (such as `print("uid=0(root)")`). Verdict labels are allowed, but the actual data must be printed alongside, and success/failure fields must be computed from the run.
5. It is **forbidden** to restate the source logic in another language and then mark `harness` (for example rewriting a Java controller in Python). What runs must be target-language code, or a compilable excerpt with the same semantics as the source.
6. **Java harnesses default to JDK 8**: write to the Java 8 language level and API (no `var`, records, text blocks, `List.of`/`Map.of`, `switch` expressions or other 9+ syntax, and no APIs that only exist in JDK 9+). The sandbox `javac` defaults to `--release 8 -encoding UTF-8`, so source may be written in UTF-8. **Do not write a `\uXXXX` escape in a comment** (javac expands `\u` before lexing, comments included). Only raise the version when the target source itself clearly requires it (`pom.xml` / `compiler.source` is 11/17, or the extracted excerpt uses that syntax), and then write `// java-release: 11` or `// java-release: 17` at the top of the source.
7. **Report gate (required before a harness Confirm)**: Write `vulns/{id}/report.md` and complete `### Vulnerable code` under `## Technical details`:
   - Give the **full in-repo relative path** of the vulnerable code (such as `src/main/java/com/foo/Bar.java` or `app/utils/backup.py:42`), not just a class or method name.
   - Paste the **source verbatim** into a fenced code block (matching what you Read, optionally with a few lines of surrounding context).
   - When the path or the code block is missing, the system rejects `ConfirmVuln(evidence_level=harness)`.
8. Verdicts:
   - The sandbox run succeeds and an attacker can produce harmful impact alone under a default deployment → write `### Vulnerable code` first, then `ConfirmVuln(evidence_level=harness)`. Write the harness to `vulns/{id}/harness.py` (or the file for that language; Confirm may pass `harness_code`). **Do not** put mocks / inlined source / the same TEST matrix into `poc.py`. The script's final output must print real runtime data, never a hard-coded success field.
   - The sandbox is unavailable, the image is missing, compilation fails, the mock will not start, or dependencies are insufficient → **do not mark a false positive**. If static analysis already proves default exploitability use `evidence_level=static_only` (and then `### Vulnerable code` is not required); otherwise continue static analysis, or state that information is insufficient and mark a false positive only when the finding itself does not hold up.
   - The harness runs and clearly does not land (parameterized query, authorization unreachable, no sensitive object on disk by default) → mark a false positive on the grounds the finding does not hold up.
9. The bar for the finding holding up is **not lowered**: source→sink reachability is not enough, and planting files or changing non-application configuration to make the finding work is forbidden. Local verification is only a source of dynamic evidence, not a reduction of the default-exploitability standard.
10. L1/L2 must not mark `dynamic` / `mcp`; **only after the system's L3 integration verification passes may the system write `dynamic`**. With no running Docker site, do not `CollectLabFingerprints` (L3 can still use the integration sandbox).
11. The sandbox has no network by default. Do not expect a harness to complete SSRF or other types that must reach the network; judge those statically.
12. **Component library audits**: Confirm on the strength of the `RunCode` harness; do not mark a false positive merely because there is no HTTP lab or no `poc.py -u`. For a pure library finding, sandbox evidence goes only into `harness.py`. Write a minimal `poc.py` as well only when the public API can be `import`ed after installing the real package (no fake `-u/--proxy`, and do not copy the harness). With neither an HTTP nor an install surface, do not write `poc.py` to disk - the API call recipe in the report is enough.
13. **Reinforced verification for request-type public APIs** (component libraries and the library core of mixed repositories; also applies in a web application when the sink sits in request-validation middleware). The component "accepts requests" when the public API's parameter is an HTTP request / middleware / routing validation input, rather than `[]byte` / `string` / a Reader. When that holds, reinforcement is required - do not just copy an internal helper such as `deepSet`:
    - Compile or import the **project's `src/`** and call that public entry point (such as `openapi3filter.ValidateRequest`); copying the sink verbatim into your own handler and treating that as the primary evidence is forbidden.
    - In the same script: an in-process test server (Go `httptest`, or an in-process client against loopback) + send the attack request + print the real status code / response / panic text. Prefer `httptest` or a short-lived listener; do not bind `0.0.0.0`, do not treat it as a Docker lab, and `evidence_level` stays `harness`.
    - The payload **must come from this request** (query / body / header); hard-coding a constant inside the handler and letting `GET /` act as a doorbell is forbidden.
    - If the whole module will not compile in the sandbox or dependencies are insufficient → fall back to the extracted function and state in the output that the public API was not reached; do not mark a false positive for that reason.
    - Do not wrap request-less APIs - YAML, `json.Unmarshal`, template `Execute`, deserialization - in HTTP you wrote yourself; that fabricates a remote attack surface. Keep calling the public function directly and print the runtime exception or return value.
